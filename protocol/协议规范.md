# VEIL（帷幕协议）——实验性加密传输协议规范 v1

> **状态：实验版（experimental），未经审计。** 本文档是 sing-box-ours 项目的旗舰差异点设计，但首先是一份诚实的文档：它写清了能做什么、不能做什么、以及每一步为什么这样设计。
>
> 版本：`VEIL-v1`（协议标识字符串，下文记为 `VEIL-v1`）· 日期：2026-11-24 · 作者：sing-box-ours 项目
>
> **铁律：不要自己造密码。** 本协议不发明任何新的密码学原件。密钥交换用 X25519、加密用 AES-256-GCM、密钥派生用 RFC 5869 HKDF-SHA256（只用标准库 `crypto/hmac` + `crypto/sha256` 手写 Extract/Expand——这是标准构造，不是新原件）。我们自己设计的只是**协议层**：握手流程、帧格式、伪装、抗主动探测、0-RTT 恢复、前向安全。WireGuard 和 Noise 就是这么做的：标准原件 + 自研协议。本规范凡是涉及密码学的地方，只做**组合与调用**，不做**发明与修改**。

## 0. 命名

- **英文代号：VEIL**
- **中文名：帷幕协议**
- **命名理由：** 帷幕遮住的是轮廓，不是存在本身——这正是本协议诚实的能力边界：它加密内容、抹平流量形状、让主动探测者得不到任何回应，但它**不宣称**让流量"隐身"或"不可检测"。一面帷幕后面仍然有人，协议不撒这个谎。其次，VEIL 简短、无空格、全大写后仍可读，便于写进链接 scheme（`veil://…`）、配置文件字段和代码标识符。`VEIL-v1` 同时是握手域分隔标签（见 §5），版本号写进密钥派生，杜绝跨版本、跨协议的密钥复用。
- **免责：** "VEIL" 是本项目的实验代号，与其他同名项目无关，不主张任何商标权利。

## 1. 设计目标与非目标

### 1.1 目标

| # | 目标 | 验收方式 |
|---|---|---|
| G1 | **机密性**：握手后全部应用数据经 AEAD 加密，窃听者得不到任何明文 | 抓包只见随机字节；错误密钥无法解密 |
| G2 | **双向认证**：客户端认证服务端长期静态密钥；服务端认证客户端静态密钥（每用户独立） | 不知道服务端公钥的客户端收不到任何回应；未登记的客户端静态密钥被静默丢弃 |
| G3 | **抗主动探测**：探测者（不知道服务端公钥）发任何字节都得不到任何回应字节 | 握手失败时服务端**零字节回包、直接关闭**（见 §8） |
| G4 | **无指纹**：握手与传输报文无固定魔数、无固定版本字段、无固定长度 | 首字节分布随机；报文长度由随机填充决定（见 §7） |
| G5 | **前向安全**：每会话使用全新临时密钥；服务端长期密钥泄露不危及历史会话 | 会话密钥全部由临时 DH 派生；定期重密钥（见 §9） |
| G6 | **重放保护**：握手与数据帧均抗重放 | 临时公钥去重缓存 + 帧 nonce 严格递增 + 会话票据单次使用（见 §10） |
| G7 | **0-RTT 恢复**：断线重连可少一次往返 | 会话票据机制（见 §11），并**诚实标注残留重放风险** |
| G8 | **可组合**：本协议只做外层，内层走 sing-box / VLESS 做路由分流 | 外层传输 VLESS 帧，不解析、不改写内层内容（见 §12） |
| G9 | **可实现、可验证**：只用 Go 标准库，零第三方依赖；原型可跑、测试可复现 | `~/workspace/sing-box-ours/protocol/` 下的原型与 `test.sh` |

### 1.2 非目标（明确不做）

- **不做匿名网络**：不隐藏 IP、不做多跳、不抗流量关联分析。需要匿名请用 Tor，本协议不是 Tor。
- **不做抗量子**：X25519 会被有足够能力的大规模量子计算机攻破（见 SECURITY.md）。抗量子密钥交换是未来版本的事，不在本版假装解决。
- **不承诺"不可检测"**：面对能做主动探测 + 机器学习流量分类的审查者，本协议的目标是**提高探测成本**（无回应、无特征），不是保证永远不被识别。任何声称"绝对无法检测"的协议都在撒谎。
- **不做用户管理**：客户端静态密钥的签发、登记、吊销由部署者（sing-box-ours 的 `install.sh` / 用户管理）负责，本协议只规定"服务端如何核验一把给定的客户端公钥"。
- **不做传输层可靠性**：本协议跑在 TCP 之上，不自己做丢包重传、拥塞控制。UDP 版本不在 v1 范围内。
- **不做密码学原件创新**：重复一遍，因为这是铁律——X25519、AES-256-GCM、HKDF-SHA256、SHA-256 全部是现成标准，参数一律取标准推荐值，不"优化"、不"改进"。

### 1.3 威胁模型

- **窃听者**：能看到全部密文，能记录、重放、篡改。目标：读明文、重放旧报文。
- **主动探测者**：能向服务端任意发字节，观察是否回包、回包长度与时延。目标：确认"这里跑着 VEIL"，进而封锁。
- **长期密钥泄露者**：某天拿到服务端长期静态私钥。目标：解密历史会话。
- **不在模型内**：端点被攻陷（密钥直接被偷走无解）、审查者有服务端合作（不在讨论范围）、量子攻击者（见非目标）。

### 1.4 与 Noise / WireGuard 的关系

- 本协议的握手是 **Noise IK 模式的改编**，不是 Noise 本身：Noise IK 的消息模式是 `-> e`、`<- e, ee, s, es`、`-> s, se`——即发起方先发临时公钥，响应方回临时公钥 + 静态公钥（用 `ee` 加密）+ 混合 `es`，发起方最后发自己的静态公钥（用 `se` 加密）。VEIL 保留了这个**密钥混合结构**（临时×静态、临时×临时、静态×临时三组 DH），但做了两处为抗探测而改的调整（见 §4 开头）：第一条消息就带认证（客户端用 `DH(e, S)` 加密自己的静态公钥），服务端在验证通过前**一个字节都不回**；Noise IK 的第一条消息是明文临时公钥，响应方无条件回包——这在抗审查场景下是不可接受的。
- WireGuard 同样是"Noise IK + 预共享静态密钥认证首包"的思路：它的握手首包就用响应方静态公钥加密，探测者得不到回应。VEIL 的 Msg1 认证借鉴的正是这一点。
- 因此：**密钥交换的结构来自 Noise IK，抗探测的首包认证来自 WireGuard 的做法，密钥派生来自 RFC 5869，加密来自 NIST 标准**。没有一行密码学是本项目发明的。

## 2. 记号与约定

- 全部整数为**大端（big-endian）**；全部长度单位为字节。
- `||` 表示字节串拼接；`X25519(a, B)` 表示以私钥 `a`、对方公钥 `B` 做 X25519 DH，结果 32 字节。
- `S` / `s`：服务端长期静态密钥对（`S_pub` 公开，随部署配置分发给客户端，相当于 Reality 的公钥）；`C` / `c`：客户端长期静态密钥对（每用户一把，公钥预先登记在服务端）；`e`：客户端临时密钥对（每会话新生成）；`f`：服务端临时密钥对（每会话新生成）。
- `HKDF-Extract(salt, IKM) -> PRK`、`HKDF-Expand(PRK, info, L) -> OKM` 为 RFC 5869，HMAC-SHA256。`salt` 为空时按 RFC 5869 用 32 字节零串代替。本规范定义辅助函数：
  `derive(IKM, salt, info) = HKDF-Expand(HKDF-Extract(salt, IKM), info, 32)`。
- AEAD 一律为 **AES-256-GCM**：密钥 32 字节，nonce 12 字节，tag 16 字节附加在密文末尾。Go 实现用标准库 `crypto/aes` + `cipher.NewGCM`。
- **为什么选 AES-256-GCM 而不是 ChaCha20-Poly1305：** 两者都是标准 AEAD，安全性相当。v1 选 AES-256-GCM 只有一个原因：**Go 标准库直接提供**（`crypto/aes`），而 ChaCha20-Poly1305 在 Go 标准库中没有（它在 `golang.org/x/crypto`，是第三方模块）。本项目"零第三方依赖"的要求优先于算法偏好；有 AES 硬件加速的机器上 AES-GCM 也更快。ChaCha20-Poly1305 列为未来可选套件，见 §13。
- 随机数一律来自密码学安全随机源（Go：`crypto/rand`），绝不用 `math/rand`。

## 3. 总览：一句话说清协议

```
客户端知道：服务端静态公钥 S_pub、自己的静态密钥 C、服务端地址
服务端知道：自己的静态私钥 s、已登记的客户端公钥表

Msg1  C -> S: e_pub || Enc(k1, C_pub || 填充)          # 首包即认证，k1 = DH(e, S)
Msg2  S -> C: f_pub || Enc(k2, S_pub || 随机数 || 填充) # k2 = DH(e,S) + DH(f,e)
Msg3  C -> S: Enc(k3, transcript_hash || 填充)          # k3 = 再混入 DH(f,C)，绑定握手 transcript
之后   双向: 帧 [长度 || AEAD(类型 || 长度 || 数据 || 随机填充)]，nonce = 计数器
```

- 握手共 1.5 个往返（Msg1 发出后即可算 k1；Msg3 发出后客户端即可发数据；服务端在验完 Msg3 后才交付数据）。
- 握手失败的**任何**一步：静默关闭，零字节回包（§8）。

## 4. 握手流程（分步）

### 4.0 为什么首包就要认证

Noise IK 的第一条消息是明文 `e`，任何人发一个 32 字节就能换来服务端的回应——这等于给探测者一个免费的"这里有人应答"信号。WireGuard / Reality 的做法是首包即认证：客户端必须先证明自己知道服务端静态公钥，否则服务端装死。VEIL 采用后者：**Msg1 本身就是一封用 `DH(e, S)` 加密的认证信**，服务端验签失败就当没听见。

### 4.1 密钥准备（握手前，带外完成）

1. 服务端生成长期静态密钥对 `(s, S_pub)`，`S_pub` 通过部署配置（sing-box-ours 的订阅/链接）安全分发给客户端。**`S_pub` 不是秘密，但它是"敲门砖"**：不知道它，就无法构造出能让服务端回应的 Msg1。
2. 客户端生成长期静态密钥对 `(c, C_pub)`，`C_pub` 预先登记到服务端授权表。吊销 = 从表中删除，即刻失效。
3. 双方约定：AEAD = AES-256-GCM；套件标识 `suite = 0x01`（含义：X25519 + AES-256-GCM + HKDF-SHA256；写在加密的 Msg1 明文内，不出现在明文头部，见 §7）。

### 4.2 Msg1：客户端 → 服务端（认证 + 亮明身份）

客户端：

1. 生成临时密钥对 `(e, e_pub)`（`crypto/rand`，用完即弃，绝不落盘）。
2. 计算 `shared1 = X25519(e, S_pub)`。
3. `k1 = derive(IKM = shared1, salt = "VEIL-v1|msg1", info = "VEIL-v1|msg1|enc")`（32 字节）。
4. 构造明文 `P1 = C_pub (32B) || suite (1B, 0x01) || pad_fixed (32B 随机)`，共 65 字节。固定 32 字节随机填充的目的是让密文长度固定（81 字节），不泄露身份长度。
5. `CT1 = AES-256-GCM-Seal(k1, nonce = 12 字节零, P1)`，共 65 + 16 = 81 字节。
6. 线上字节 `W1 = len (uint16 BE, = 32 + 81 + len(pad_outer)) || e_pub (32B) || CT1 (81B) || pad_outer (0–256 字节随机)`。`pad_outer` 长度每会话随机，`len` 字段随之变化——**没有固定报文长度**。

服务端收到后：

1. 读 2 字节 `len`（须在 `[113, 113+256]` 区间内，否则静默关闭）；读满 `len` 字节，超时 10 秒。
2. 取 `e_pub`、`CT1`，算 `shared1' = X25519(s, e_pub)`，`k1'` 同上，尝试解密 `CT1`。**解密失败 → 静默关闭**（不回字节、不记日志，见 §8）。这一步同时挡住了两类探测者：不知道 `S_pub` 的（算不出 `shared1`）、乱发字节的（AEAD 认证失败）。
3. 解密成功后取 `C_pub`，查授权表：**未登记 → 静默关闭**；`suite != 0x01` → 静默关闭。
4. 查临时公钥去重缓存：`e_pub` 在过去 5 分钟内出现过 → 疑似重放，静默关闭；否则记入缓存（带过期时间，有界容量，见 §10）。

> 注意：到这一步为止，服务端**一个字节都没有回**。探测者从服务端行为上无法区分"端口没开"、"不是 VEIL"、"密钥错了"三种情况——这正是想要的效果。

### 4.3 Msg2：服务端 → 客户端（服务端认证 + 临时密钥交换）

服务端：

1. 生成临时密钥对 `(f, f_pub)`。
2. 计算 `shared2 = X25519(f, e_pub)`。
3. `k2 = derive(IKM = shared1 || shared2, salt = "VEIL-v1|msg2", info = "VEIL-v1|msg2|enc")`。
4. 明文 `P2 = S_pub (32B) || server_random (16B 随机) || pad_fixed (32B 随机)`，共 80 字节。
5. `CT2 = AES-256-GCM-Seal(k2, nonce = 12 字节零, P2)`，共 96 字节。
6. 线上字节 `W2 = len (uint16 BE) || f_pub (32B) || CT2 (96B) || pad_outer (0–128 字节随机)`。

客户端收到后：

1. 读 `len`、读满；`len` 须在 `[128, 128+128]` 内，否则关闭。
2. 算 `shared2' = X25519(e, f_pub)`，`k2'` 同上，解密 `CT2`。失败 → 关闭（客户端可以记日志，这是客户端自己的事）。
3. 核对解密出的 `S_pub` 与本地配置的服务端公钥**逐字节相等**。不等 → 服务端是假的，关闭。这一步完成**服务端认证**：只有持有 `s` 的服务端才能算出 `shared1` 从而构造出能被 `k2` 解开的 Msg2。
4. 保存 `server_random`（混入会话密钥派生，见 §5）。

### 4.4 Msg3：客户端 → 服务端（客户端认证 + transcript 绑定）

客户端：

1. 计算 `shared3 = X25519(c, f_pub)`（客户端静态 × 服务端临时，即 Noise IK 的 `se`）。
2. `k3 = derive(IKM = shared1 || shared2 || shared3, salt = "VEIL-v1|msg3", info = "VEIL-v1|msg3|enc")`。
3. 计算 `transcript = SHA-256(W1 || W2)`，其中 `W1`、`W2` 是双方实际收发的线上字节（含 `len` 前缀与外层随机填充）。这一步把**整个握手历史**绑进 Msg3：中间人哪怕只改了一个填充字节，transcript 都会对不上。
4. 明文 `P3 = transcript (32B) || pad_fixed (32B 随机)`，共 64 字节；`CT3 = AES-256-GCM-Seal(k3, nonce = 12 字节零, P3)`，共 80 字节。
5. 线上字节 `W3 = len (uint16 BE) || CT3 (80B) || pad_outer (0–128 字节随机)`。

服务端收到后：

1. 读 `len`、读满；算 `shared3' = X25519(f, C_pub)`，`k3'` 同上，解密 `CT3`。失败 → 静默关闭。
2. 核对解密出的 `transcript` 与本地算的 `SHA-256(W1 || W2)` 相等。不等 → 静默关闭。
3. 通过。此时服务端确信：对端持有 `C` 的私钥（`shared3` 只有 `C` 的持有者能算出），且握手未被篡改。**客户端认证完成**。

### 4.5 握手完成后的状态

双方按 §5 派生传输密钥，进入 §6 的帧传输。服务端在验完 Msg3 后，立即发一个**会话票据帧**（类型 `0x02`，见 §11）给客户端，供下次 0-RTT 恢复使用；客户端收到后可落盘保存（文件权限 `0600`，内容本身是敏感的）。

## 5. 会话密钥派生（HKDF，RFC 5869）

### 5.1 输入

握手结束时双方共享：

| 值 | 来源 | 长度 |
|---|---|---|
| `shared1` | `X25519(e, S)` = `X25519(s, e)` | 32B |
| `shared2` | `X25519(f, e)` = `X25519(e, f)` | 32B |
| `shared3` | `X25519(c, f)` = `X25519(f, C)` | 32B |
| `transcript` | `SHA-256(W1 \|\| W2)` | 32B |
| `server_random` | Msg2 明文内 16B 随机数 | 16B |

### 5.2 派生步骤（双方算出完全相同的结果）

```
master_secret = HKDF-Extract(salt = "VEIL-v1|master", IKM = shared1 || shared2 || shared3)
master        = HKDF-Expand(master_secret, info = "VEIL-v1|master|" || transcript, L = 32)
k_c2s         = HKDF-Expand(master, info = "VEIL-v1|c2s", L = 32)   # 客户端 -> 服务端
k_s2c         = HKDF-Expand(master, info = "VEIL-v1|s2c", L = 32)   # 服务端 -> 客户端
```

> 为什么这样分：(1) `salt` 与 `info` 里都带 `VEIL-v1` 域分隔标签，密钥绝不会被拿到别的协议里复用；(2) `transcript` 混入 `master` 的 info，保证**不同握手历史派生出不同会话密钥**，握手被篡改则双方密钥不一致、首帧即解密失败；(3) 两个方向用不同 `info` 派生不同密钥，**方向隔离**：一个方向的密钥泄露不影响另一方向，且反射攻击（把客户端的密文原样发回给客户端）必然解密失败；(4) 三组 DH 全部混入：`shared1` 绑定服务端静态身份，`shared2` 提供临时性，`shared3` 绑定客户端静态身份——任何一组缺失都会导致密钥不同。

### 5.3 为什么是 HKDF 而不是"直接 SHA-256 拼接"

直接 `SHA-256(shared1 || shared2 || ...)` 是"能跑但不规范"的做法：它没有 salt、没有 info 域分隔、没有可证明的安全归约。HKDF（RFC 5869）是为"从有偏的 DH 共享秘密提取均匀密钥"这个**恰好**的问题设计的标准构造，有形式化安全证明，且 Go 标准库 `crypto/hmac` + `crypto/sha256` 几十行就能写对。本规范的 HKDF 实现（原型 `veil.go` 中 `hkdfExtract` / `hkdfExpand`）逐行对照 RFC 5869 §2.2/§2.3，并用 RFC 5869 附录 A 的测试向量自检（见原型测试）。

### 5.4 前向安全说明

`shared2` 来自每会话新生成的临时密钥 `e`、`f`，会话结束后临时私钥即丢弃（内存清零，不落盘）。因此即使服务端长期私钥 `s` 将来泄露，攻击者也只能算出 `shared1`，算不出 `shared2`（需要 `e` 或 `f` 的私钥），也就恢复不出 `master`——**历史会话仍安全**。这是 Noise IK / WireGuard 同款前向安全，代价是每会话一次 X25519 临时密钥生成（微秒级，可忽略）。

## 6. 帧格式（传输层）

握手完成后，应用数据（内层 VLESS 帧）以如下帧格式双向传输：

```
线上字节：
  len    : uint16 BE，= CT 的长度（即 明文长度 + 16 字节 GCM tag）
  CT     : AES-256-GCM 密文

明文（解密后）：
  type   : 1B    帧类型
  padlen : 1B    末尾随机填充长度 N（0–255）
  payload: 变长  应用数据（内层 VLESS 帧的字节，原样搬运）
  pad    : N 字节 随机填充
```

- **明文总长度上限 16384 字节**（含 `type` + `padlen` + `payload` + `pad`）。超长应用数据由发送方自行分片。`len` 最大值为 16384 + 16 = 16400；收到 `len > 16400` 或 `len < 18`（最短：type + padlen + 0 字节 payload + 0 填充 + 16 tag）的帧 → 关闭连接。
- **nonce**：12 字节 = `0x00000000 || uint64 BE 计数器`。每方向独立计数器，从 0 开始，每帧 +1。**nonce 绝不重复使用**：同一密钥下计数器耗尽前必须重密钥（见 §9）。计数器是 AEAD nonce 的一部分，不在线上传输——窃听者看不到它，也就无法从 nonce 推断帧序号。
- **帧类型**：

| type | 名 | 含义 |
|---|---|---|
| `0x00` | chaff | 填充帧：payload 为空，全是随机填充。接收方直接丢弃。用于流量整形（可选，见 §7）。 |
| `0x01` | data | 应用数据帧：payload 是内层 VLESS 帧字节。 |
| `0x02` | ticket | 会话票据帧（仅服务端 → 客户端）：payload = `ticket_id (16B) \|\| resumption_secret (32B) \|\| expiry_unix (8B BE)`。见 §11。 |
| `0x03` | close | 关闭帧：payload 为空。收到后可优雅关闭（仍须先处理完之前已收到的帧）。 |
| `0x04` | early-end | 0-RTT 早期数据结束标记（仅 0-RTT 恢复时客户端 → 服务端）：payload 为空。见 §11。 |

- **AEAD 附加数据（AAD）**：本版 `AAD = 空`。帧长度已由 `len` 字段承载且密文认证覆盖全部明文，不再另加 AAD（保持实现简单；未来版本如需绑定方向/帧序号，可把 `type || 计数器` 做 AAD，见 §13）。
- **乱序 / 丢失**：TCP 保证按序到达；接收方仍校验 nonce 计数器**严格递增**（期望值 = 上一帧 +1）。收到计数器不符的帧（重放旧帧、跳号、乱序）→ 立即关闭连接。这是数据帧的重放保护（§10）。

## 7. 填充与伪装

目标不是"让流量看起来像 HTTPS"（那是 Reality 的活，本协议不抢），而是**让流量没有可供字符串匹配和长度分析的固定特征**：

1. **无固定魔数**：协议任何位置都没有 magic bytes、没有明文版本号、没有固定握手前缀。首字节是 `len` 字段的高字节——握手报文长度随机，首字节分布接近均匀；传输帧的 `len` 同样随 payload 与填充变化。
2. **随机填充（三处）**：
   - 握手报文外层填充：Msg1 0–256 字节、Msg2/Msg3 0–128 字节，每会话随机；
   - 握手报文内层固定填充：Msg1/Msg2/Msg3 明文各含 32 字节固定随机填充，保证密文长度固定、不泄露身份字段长度；
   - 数据帧内层填充：每帧 `padlen` 在 0–255 间均匀随机，`pad` 为真随机字节。
3. **长度分布**：由于填充的存在，相同长度的应用数据在线上呈现为分布在 `[真实长度, 真实长度+255]` 区间内的随机长度。`len` 字段本身是 framing 必需的（TCP 是流，必须知道帧边界），但它不携带任何协议标识信息——任何长度前缀协议都有它。
4. **填充帧（chaff，type `0x00`）**：发送方可在空闲时或按策略发送全填充帧，抹平"有数据/无数据"的时序特征。本版原型**不主动发 chaff**（实现留接口，默认关闭），因为无节制的 chaff 等于自找带宽浪费；是否开启、何种速率，由部署者按需决定，并在 SECURITY.md 中诚实说明：chaff 只能增加分析成本，不能保证抗流量分析。
5. **诚实边界**：填充防的是**基于固定特征的匹配**（魔数、固定长度、固定握手），不防**基于统计的流量分类**（包大小分布、时序、双向流量比）。后者需要持续的流量整形与恒定速率发送，本版不承诺。

## 8. 抗主动探测：静默丢弃

**规则（服务端，铁律）：握手认证失败时，不回任何字节，直接关闭 TCP 连接。**

| 触发条件 | 服务端行为 |
|---|---|
| 首包超时（10 秒内未收满） | 关闭，不回包 |
| `len` 不在合法区间 | 关闭，不回包 |
| Msg1 AEAD 解密失败 | 关闭，不回包 |
| `C_pub` 未登记 / `suite` 非法 | 关闭，不回包 |
| `e_pub` 5 分钟内重复出现 | 关闭，不回包 |
| Msg3 解密失败 / transcript 不符 | 关闭，不回包 |
| 传输帧 AEAD 失败 / nonce 不符 / 长度非法 | 关闭，不回包 |
| 任意时刻收到无法解析的字节 | 关闭，不回包 |

- **不回包**指 TCP 层面不发送任何应用层字节（关闭连接本身的 FIN/RST 是 TCP 语义，无法避免，也不必避免——端口扫描器对关闭端口和静默丢弃的服务看到的都是"无应用层回应"）。
- **不记日志**：认证失败不写访问日志（零日志哲学；排障用的 debug 日志默认关闭，开启时也只记"某 IP 在某时握手失败"，不记报文内容）。原型为便于测试把失败原因写到服务端**标准错误输出**（stderr），生产部署须关闭——见 SECURITY.md。
- **时序**：失败后立即关闭，不加随机延迟。加延迟看似能防时序分析，实则引入可测量的时序特征；立即关闭是最简单、最一致的行为。
- **客户端侧**：客户端在握手失败时可以记日志、可以重试（应加退避），这是客户端的自由；服务端不配合、不给任何信息。

## 9. 前向安全与重密钥

1. **每会话临时密钥**：`e`、`f` 每会话新生成，会话结束即丢弃（内存清零）。长期密钥 `s`、`C` 只用于认证，不直接加密任何应用数据。
2. **定期重密钥（rekey）**：同一传输密钥的使用上限为以下三者之先到者——
   - 发送/接收帧数达到 **65536 帧**，或
   - 任一方向传输明文累计达到 **256 MiB**，或
   - 会话持续 **900 秒（15 分钟）**。
   触发时双方**无需协商**，按同一确定性规则各自派生新密钥：
   `k_new = HKDF-Expand(k_old, info = "VEIL-v1|rekey|" || uint64 BE epoch, L = 32)`，其中 `epoch` 从 1 开始递增；nonce 计数器随新密钥重置为 0。重密钥是单向独立的（c2s 与 s2c 各自按各自的帧计数触发）。
   > 这样设计的原因：nonce 是 64 位计数器，2^64 帧才耗尽，实际永远到不了；重密钥的真正意义是**限制单密钥加密的数据量**（把 GCM nonce 误用与密钥泄露的影响面控制在一个窗口内），以及让长期会话不依赖单一密钥。
3. **0-RTT 票据不参与前向安全**：票据恢复的会话仍会立即走完整握手生成新的临时密钥（见 §11），早期数据密钥只保护少量首包数据。

## 10. 重放保护

| 层 | 机制 | 窗口 / 说明 |
|---|---|---|
| 握手 Msg1 | 服务端缓存最近 5 分钟内见过的 `e_pub`（有界 LRU/带过期清理，容量上限 100000 条，满了挤掉最旧的）。重复出现 → 静默关闭。 | 攻击者重放整条 Msg1 只能换来一次关闭；且重放的 Msg1 即便通过，也只能走到 Msg2——没有 `C` 的私钥算不出 Msg3，拿不到传输密钥。 |
| 数据帧 | 每方向 nonce 计数器严格递增，收到期望值之外的帧立即关闭连接。 | TCP 有序到达，重放旧帧的计数器必然小于期望值，立即发现。 |
| 会话票据 | 票据 ID 单次使用：服务端票据表命中即标记 `used`，二次使用直接拒绝（见 §11）。 | 票据有效期 600 秒，过期自动失效。 |

## 11. 0-RTT：会话票据恢复

### 11.1 票据签发（完整握手后）

1. 服务端在验完 Msg3 后生成：`ticket_id`（16B 随机）、`resumption_secret`（32B 随机）、`expiry = now + 600 秒`。
2. 服务端在内存票据表记录 `ticket_id -> {resumption_secret, expiry, used=false}`（重启即失，票据随之失效——可接受，客户端回退到完整握手）。
3. 服务端用传输密钥发一个类型 `0x02` 的票据帧，payload 为 `ticket_id || resumption_secret || expiry_unix`。客户端保存到票据文件（`0600` 权限）。

### 11.2 0-RTT 恢复流程

客户端持有未过期票据时：

1. 生成新临时密钥对 `(e', e'_pub)`，算 `shared_e = X25519(e', S_pub)`。
2. 派生两个密钥：
   - `k_auth = derive(IKM = shared_e || resumption_secret, salt = "VEIL-v1|0rtt", info = "VEIL-v1|0rtt|auth")`——用于认证恢复请求；
   - `k_data = derive(IKM = resumption_secret || shared_e, salt = "VEIL-v1|0rtt", info = "VEIL-v1|0rtt|data")`——用于加密早期数据帧。
3. 发恢复请求 `W1' = len || e'_pub (32B) || ticket_id (16B 明文) || CT' (81B) || pad_outer (0–256B)`，其中 `CT'` 是用 `k_auth`、nonce 全零加密的 `P1`（与 Msg1 相同结构：`C_pub || suite || 32B 随机填充`）。`ticket_id` 以明文放在外层——它是 16 字节真随机数，本身不泄露任何信息，服务端靠它查表取回 `resumption_secret`。
4. **无需等待**，立即用 `k_data` 发早期数据帧（type `0x01`，nonce 计数器从 0 计），然后发一个 `early-end` 帧（type `0x04`）表示早期数据发完了。
5. 再按 §4.3/§4.4 走 Msg2/Msg3，完成完整握手，派生全新传输密钥；之后的帧改用传输密钥。

服务端收到恢复请求后：

1. 先按 Msg1 试解密，失败再按恢复请求试解密（取 `ticket_id` 查表；查不到 / 已用过 / 已过期 → 静默关闭）。
2. 查到且有效 → **立即标记 `used=true`**（先标记、后解密，这是防重放的关键顺序），用 `k_auth` 解密 `CT'` 验 `C_pub` 与 `suite`。
3. 用 `k_data` 读早期数据帧，直到 `early-end` 帧；**先缓存、不交付**——早期数据要等 Msg3 验完（完整握手成功）才交付给应用层。握手失败则整批丢弃。
4. 发 Msg2、收 Msg3、验 transcript，派生传输密钥，交付缓存的早期数据，回发新票据（旧票据已作废，一次一票）。

### 11.3 诚实写清：0-RTT 的重放残留风险

**0-RTT 数据在密码学上就是可重放的，这是 TLS 1.3 也有、谁也绕不开的结论**，原因：早期数据只由票据密钥 + 新临时密钥保护，服务端在"标记票据已用"之前无法区分"第一次送达"与"攻击者原样重放"。VEIL 的缓解措施只能缩小窗口，不能清零风险：

- 票据**单次使用**：服务端收到即标记，第二次送达直接拒绝。攻击者只有在"原始请求仍在路上、服务端尚未标记"的**竞态窗口**（毫秒级）内重放才可能得逞。
- 票据**有效期 600 秒**：过期票据直接拒绝，攻击者没有"录下来下周再放"的机会。
- 早期数据**先缓存、握手成功后才交付**：握手失败则早期数据作废，攻击者无法用重放的早期数据骗取"未完成握手的服务端的回应"。
- **残留风险（必须承认）**：在竞态窗口内，同一份早期数据可能被服务端交付两次。如果早期数据是"内层 VLESS 的一次普通代理请求"，重放的后果是同一请求被执行两次——对幂等的读请求无害，对"扣费/下单/发帖"类非幂等操作有害。**缓解建议**：0-RTT 只用于恢复连接、只携带首个内层请求；应用层（VLESS 之上的业务）应对非幂等操作自己做去重。默认策略：**0-RTT 是可选项，默认关闭**，由部署者在"快 1 个 RTT"与"残留重放风险"之间自己选择。原型实现 0-RTT 供验证，`test.sh` 会测通它，但生产默认建议关闭。

## 12. 与 sing-box / VLESS 的集成

### 12.1 分层

```
应用流量
  └─ VLESS 帧（sing-box 负责：路由、分流、用户、订阅）
      └─ VEIL 帧 type 0x01（本协议：加密 + 填充 + 抗探测）
          └─ TCP
```

- **VEIL 只做外层**：它不知道、也不解析内层 VLESS 的内容。`type 0x01` 的 payload 就是 VLESS 客户端发来的字节流的切片，原样搬运、原样交还。内层的 UUID、路由规则、分流策略、订阅，全部是 sing-box 的事。
- 服务端收到 VEIL 帧、解密后，把 payload 交给本地 sing-box 的 VLESS 入站（本机回环 TCP/Unix socket）；sing-box 的回包再包进 VEIL 帧发回。原型用 **echo** 代替真实的 sing-box 入站（只证明外层能跑），集成时把 echo 换成到 sing-box 的转发即可，握手与帧格式一行不用改。
- 部署形态（目标）：`install.sh` 生成服务端静态密钥 `S`，写进 VEIL 服务端配置；客户端链接形如 `veil://<S_pub_base64url>@<host>:<port>?client=<C_pub>…`（链接格式待定，不属本规范 v1 的强制内容）；sing-box 客户端通过本地 VEIL 进程或将来的 sing-box 原生入站/出站接入。

### 12.2 为什么外层不直接复用 TLS / Reality

因为 VEIL 的定位是**与 Reality 并列的另一条主力线**，不是替代品：Reality 借真实网站的 TLS 握手，强在"看起来像正常网站"；VEIL 强在"首包即认证 + 零回应探测 + 随机填充"，两者被针对的特征面不同，互为备份。这正是 sing-box-ours "多协议一次装齐、互为备份"的哲学：**不要把所有鸡蛋放在一种伪装上**。

## 13. 版本、套件与未来工作

- **版本标识**：`VEIL-v1` 只出现在密钥派生的 `salt`/`info` 与文档中，不出现在任何明文报头。升级版本 = 换一套域分隔标签，旧版密钥与新版密钥天然隔离。
- **套件**：v1 唯一套件 `0x01` = X25519 + AES-256-GCM + HKDF-SHA256。预留：`0x02` = X25519 + ChaCha20-Poly1305（需引入 `golang.org/x/crypto` 或等价实现，见 §2 说明）；`0x03` 及以后 =  post-quantum 混合密钥交换（如 X25519+ML-KEM），待标准与实现成熟后再议，**不在 v1 假装支持**。
- **未来工作**：见 SECURITY.md §5（审计、fuzz、互通测试、形式化分析、UDP 传输、恒定速率整形）。

| `k_data` (0-RTT) | `resumption_secret \|\| shared_e` | `VEIL-v1\|0rtt` | `VEIL-v1\|0rtt\|data` | 早期数据帧 |
| `k_new` (rekey) | Expand(`k_old`) | — | `VEIL-v1\|rekey\|` + `uint64 BE epoch` | 重密钥 |

> 注：HKDF-Extract 的 `salt` 为空时用 32 字节零串（RFC 5869 §2.2）；本规范所有 Extract 调用都显式传了 salt，不存在空 salt 的情况。

## 附录 C：术语

- **AEAD**：带关联数据的认证加密（Authenticated Encryption with Associated Data）。AES-256-GCM 是 AEAD 的一种：加密同时给出认证 tag，篡改密文必然导致解密失败。
- **HKDF**：基于 HMAC 的密钥派生函数（RFC 5869），分 Extract（提取）与 Expand（扩展）两步。
- **前向安全（Forward Secrecy）**：长期密钥泄露后，历史会话仍不可解密的性质。
- **0-RTT**：零往返恢复——客户端无需等待服务端回应即可先发数据，代价是残留重放风险（见 §11.3）。
- **Transcript**：握手全程实际收发的字节，用于绑定握手历史、防篡改。
