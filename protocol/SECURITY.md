# SECURITY.md — VEIL（帷幕协议）安全声明

> **实验版、未经审计。** 本文档是 VEIL v1 必须附带的安全声明，与协议规范同等重要。
> 阅读本协议或部署本原型之前，请先读完本文。

---

## 1. 一句话定性

**VEIL v1 是一个实验性协议：设计上遵循了"标准原件 + 自研协议"的正确方法，但它未经审计、未经形式化分析、未经互通测试、未经长期实战检验。**

它可以用于学习、实验和内部测试。**不要**把它当作已验证安全的生产加密方案，不要用它传输你输不起的数据，不要向用户承诺它"绝对安全"——**没有任何人可以对一个未经审计的实验协议做这种承诺，包括我们自己。**

---

## 2. 明确不承诺的事（不许写"绝对安全"）

- 不承诺"绝对安全"、"无法破解"、"无法检测"、"军用级加密"——这些词在本项目是禁语。
- 不承诺抗量子、不承诺抗流量分析、不承诺抗端点攻陷。
- 不承诺与 Noise / WireGuard / TLS 同等的安全强度——我们借鉴了它们的结构，但**借鉴结构不等于继承安全证明**。每一次改编（首包认证、票据机制、重密钥规则）都可能引入原协议没有的问题。

---

## 3. 已知局限

| # | 局限 | 影响 | 状态 |
|---|---|---|---|
| L1 | **无形式化分析**：握手与密钥派生没有经过 ProVerif / Tamarin 等工具的形式化验证，也没有安全证明 | 可能存在设计层面的逻辑漏洞（如状态机绕过、密钥复用边界条件） | 待做（见 §5） |
| L2 | **无抗量子**：X25519 可被有足够能力的大规模量子计算机攻破 | 长期保密性在量子时代不成立；"现在记录、将来解密"（harvest-now-decrypt-later）的攻击者可针对长期高价值流量 | 未来版本考虑 X25519+ML-KEM 混合 |
| L3 | **侧信道未处理**：原型未做恒定时间实现之外的侧信道防护；无内存锁定（mlock）、无密钥内存清零的系统性保证、未考虑缓存时序与功耗分析 | 同机攻击者或有精细计时能力的攻击者可能提取信息 | 待评估；生产实现须补 |
| L4 | **0-RTT 重放残留风险**：见规范 §11.3。票据单次使用 + 600 秒有效期只能把重放窗口缩到毫秒级竞态，不能清零 | 同一份早期数据可能被服务端交付两次；非幂等操作（扣费、下单、发帖）可能被重复执行 | 已缓解、未消除；默认建议关闭 0-RTT |
| L5 | **单实现、无互通测试**：只有一个 Go 实现，没有第二实现对照，没有跨语言、跨平台测试 | 实现 bug（如 nonce 计数不同步、帧边界处理）可能在互通时才暴露；也无法用"两个独立实现一致"来佐证规范无歧义 | 待做（见 §5） |
| L6 | **无 fuzz 测试**：握手解析、帧解析尚未经过覆盖率引导的 fuzz | 畸形输入可能导致崩溃、 panic 或非预期的状态机转移 | 待做（见 §5） |
| L7 | **抗流量分析有限**：随机填充只能抹平固定特征，不能对抗统计流量分类、时序分析与双向流量关联 | 面对有机器学习分类能力的审查者，VEIL 只能提高成本，不能保证不被识别 | 诚实边界，见规范 §7 |
| L8 | **服务端票据状态在内存**：票据表、临时公钥去重缓存都在进程内存，重启即失；去重缓存有界（10 万条），超量时挤掉最旧条目 | 服务端重启后旧票据全部失效（客户端回退完整握手，可接受）；去重缓存被挤掉的条目在 5 分钟窗口内可能被重放一次（但重放仍需过 Msg3 的私钥认证，拿不到传输密钥） | 已知、可接受 |
| L9 | **无证书 / 公钥分发安全**：`S_pub` 靠部署配置带外分发；分发过程被篡改则客户端会信任假服务端（首次使用信任问题，TOFU） | 与 Reality / WireGuard 的公钥分发问题相同，不是本协议能独立解决的 | 部署层责任，见 §4 |
| L10 | **原型日志**：原型服务端把握手失败原因写到 stderr（为测试可观测）；生产若照抄，等于把探测记录写进日志 | 违反零日志哲学，且日志本身可能成为信息源 | 生产部署必须关闭（见 §4） |

## 4. 安全使用要求（部署者必读）

1. **密钥管理**：服务端长期静态私钥 `s` 与客户端私钥 `c` 是安全的根。生成用 `crypto/rand`，存储权限 `0600`，**绝不**写进文档、聊天记录、代码仓库或日志；泄露后立即轮换（重新生成并重新分发 `S_pub`、重新登记 `C_pub`）。
2. **公钥分发**：`S_pub` 必须通过可信渠道分发（如 sing-box-ours 本地生成的订阅文件）。不要通过未加密的聊天、邮件明文传递。
3. **关闭原型日志**：生产部署须关闭服务端 stderr 的握手失败日志（或只记计数、不记原因与地址），恢复零日志默认。
4. **0-RTT 默认关闭**：除非你理解 §11.3 的残留风险并确认内层业务幂等，否则不要开启 0-RTT。
5. **保持更新**：Go 工具链与标准库的安全更新要跟进；发现漏洞时按 §6 的流程报告。
6. **不要混用密钥**：`S`/`C` 密钥对只用于 VEIL，不挪作他用；不同部署（不同服务器）用不同密钥对。
7. **票据文件**：客户端票据文件含 `resumption_secret`，权限 `0600`，视同短期凭证保管；泄露后服务端重启即失效（票据表在内存）。

## 5. 下一步要做的事

按优先级排序，做完一项勾一项：

- [ ] **审计**：请独立的密码学审计者审规范 + 实现（握手状态机、密钥派生、nonce 管理、票据逻辑为重点）。
- [ ] **形式化分析**：用 ProVerif 或 Tamarin 对握手做建模，验证机密性、认证性、前向安全。
- [ ] **Fuzz**：对握手解析与帧解析做覆盖率引导的 fuzz（Go 原生 `testing.Fuzz` 即可，标准库内完成），跑出畸形输入下的崩溃与 panic。
- [ ] **互通测试**：写第二实现（建议 Python 标准库版，与 Go 版对跑握手与 echo），验证规范无歧义。
- [ ] **测试向量**：发布固定密钥、固定随机数下的握手全程测试向量（Msg1/Msg2/Msg3/首帧密文），供第三方实现对照。
- [ ] **重密钥实测**：把重密钥阈值临时调小，实测长会话跨越重密钥边界后双方仍能正常通信。
- [ ] **侧信道评估**：检查关键路径的恒定时间性；补密钥内存清零与 mlock。
- [ ] **ChaCha20-Poly1305 套件**（`0x02`）：面向无 AES 硬件加速的设备，需引入 `golang.org/x/crypto` 或等价实现，并重新评估"零第三方依赖"的取舍。
- [ ] **抗量子路线评估**：跟踪 ML-KEM 标准化与实现成熟度，评估 X25519+ML-KEM 混合握手的成本。
- [ ] **与 sing-box 的真实集成**：把原型的 echo 换成到本地 sing-box VLESS 入站的转发，跑通端到端代理，再谈"主力线"。

## 6. 漏洞报告

发现 VEIL 的安全问题，请通过 sing-box-ours 项目的公开渠道报告（不要在公开 issue 里贴可利用的细节与真实密钥）。报告应包含：影响的版本、复现步骤、你认为的影响范围。我们承诺：**收到报告先复现、再修、再公开，不隐瞒、不淡化**——诚实面对局限是这个项目哲学的核心，安全问题上更是如此。

VEIL 是开源实验项目，按"现状"提供，不附带任何明示或暗示的保证。部署者自行承担使用风险。因使用本协议导致的任何损失，项目不承担责任。**如果你需要经过验证的生产级加密传输，请使用 WireGuard、TLS 1.3 或其他经过长期审计的成熟方案**——在 VEIL 完成 §5 的清单之前，它不是这些方案的替代品。
